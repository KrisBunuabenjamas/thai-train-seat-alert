# ระบบแจ้งเตือนที่นั่งรถไฟกลับมาว่าง

## เป้าหมาย
เฝ้าตรวจกรุงเทพอภิวัฒน์ → อุดรธานี วันที่ออกเดินทาง 29 และ 30 ธันวาคม 2026 แล้วแจ้ง Discord เมื่อที่นอนกลับมาว่าง ให้ผู้ใช้เปิด D-Ticket ไปจองเอง ตรวจทุกประเภทตู้นอนและทุกขบวนที่ API ส่งกลับ โดยแสดงข้อจำกัดผู้โดยสารของตู้ให้ชัดเจน

API บอกจำนวนที่ว่าง ไม่บอกสาเหตุ จึงแจ้งว่า “พบที่นั่งกลับมาว่าง” โดยไม่ยืนยันว่าเกิดจากการยกเลิก

## วิธีทำงาน
Python ทำงานหนึ่งรอบต่อหนึ่ง GitHub Actions run ตั้ง schedule ทุก 5 นาทีและมีปุ่มรันเอง ใช้ standard Linux runner บน public repository ตารางเวลาอาจล่าช้าหรือข้ามรอบ ไม่รับประกันตรวจพบที่ว่างช่วงสั้น ๆ

สร้าง anonymous HTTP session ใหม่ในแต่ละรอบ เปิดหน้า home และ POST แบบค้นหาเพื่อรับ page state จากนั้นเรียก getTrip และ getTrainCoach ตามรูปแบบที่ตรวจสอบจาก JavaScript ของ D-Ticket แล้ว อัปเดต viewStateHolder ตามคำตอบ ไม่เก็บ session cookie ลง repository หรือ logs ไม่ต้องใช้รหัสผ่านผู้ใช้

แยกส่วน HTTP client, การเปรียบเทียบสถานะ, Discord sender และตัวเรียกหนึ่งรอบ เพื่อทดสอบได้โดยไม่ยิงเว็บจริงซ้ำ

## สถานะและการแจ้งเตือน
เก็บสถานะ JSON ใน branch สำหรับสถานะของ repository แยก key ตามวัน ต้นทาง ปลายทาง ขบวน และ coachId มีเวลาอ่านสำเร็จล่าสุดและรายการแจ้งเตือนค้างส่ง ใช้ workflow concurrency กลุ่มเดียว และอ่าน branch ล่าสุดทุกครั้งก่อนประมวลผล

- ครั้งแรกถือค่า baseline เป็น FULL เพื่อแจ้งทันทีหากตรวจพบว่าง
- FULL → AVAILABLE: แจ้งวันเดินทาง ขบวน เวลาออก ประเภทตู้ ข้อจำกัดผู้โดยสาร จำนวนว่าง เวลาตรวจ และลิงก์หน้า D-Ticket
- AVAILABLE → AVAILABLE: ไม่แจ้งซ้ำ แม้จำนวนเพิ่ม
- AVAILABLE → FULL → AVAILABLE: แจ้งอีกครั้ง
- Error หรือรายการหาย: ไม่เปลี่ยนสถานะที่ตรวจสำเร็จล่าสุด ไม่ตีความเป็น FULL
- อ่าน state ไม่ได้หรือเสียหาย: หยุดรอบและรายงานข้อผิดพลาด ไม่ตั้ง baseline ใหม่เงียบ ๆ
- บันทึก pending event ก่อนส่ง Discord และยืนยันการส่งหลัง Discord ตอบรับสำเร็จเท่านั้น รอบถัดไปตรวจว่าที่นั่งยังว่างก่อนส่งรายการค้าง เพื่อไม่ส่งข้อมูลเก่า
- Discord และ Git ไม่ใช่ธุรกรรมเดียวกัน หากส่งสำเร็จแต่บันทึกผลไม่ได้อาจแจ้งซ้ำได้ ไม่อ้างว่าป้องกันซ้ำได้ 100% ในกรณีระบบล้มเหลวระหว่างทาง

## ความต่อเนื่องและการตั้งค่า
เก็บ DISCORD_WEBHOOK_URL ใน GitHub Actions Secret เท่านั้น ใช้ timeout และ retry แบบจำกัดพร้อม backoff สำหรับปัญหาชั่วคราว เคารพ Retry-After และไม่พยายามข้าม CAPTCHA หรือระบบควบคุมการเข้าถึง

บันทึก heartbeat ของการตรวจแต่ละรอบใน state branch จึงมี repository activity ต่อเนื่องในช่วงเฝ้าตรวจ ต้องตรวจว่า workflow ยังเปิดอยู่และ run ล่าสุดสำเร็จ ไม่ใช้ heartbeat ของ workflow ตัวเองเป็นหลักประกันว่าระบบตรวจจับการหยุดรันได้ทั้งหมด หากผิดพลาดต่อเนื่อง 3 รอบให้แจ้งปัญหา Discord ครั้งเดียว และแจ้งเมื่อกลับมาทำงานได้ กรณี Discord ใช้ไม่ได้ให้ workflow fail เพื่อเห็นใน GitHub

หยุดตรวจแต่ละขบวนเมื่อถึงเวลาออกใน Asia/Bangkok และออกโดยไม่เรียก D-Ticket หลังพ้นวันเดินทางทั้งหมด ไม่สร้างบริการ Firebase หรือระบบจองอัตโนมัติ

## การตรวจรับ
ทดสอบ transition, error ระหว่าง FULL/AVAILABLE, ข้อมูลบางส่วนหาย, state เสียหาย, ส่ง Discord ไม่สำเร็จ, pending event หมดความเกี่ยวข้อง, schema ผิด และตัดวันหมดอายุ ใช้ข้อมูลตัวอย่างที่ไม่มี secrets

รัน dry-run กับ API จริงทั้งสองวัน แล้วทดสอบข้อความ Discord เมื่อผู้ใช้ตั้ง Secret ให้ ทดสอบ workflow บน GitHub runner จริงก่อนระบุว่าเปิดเฝ้าตรวจแล้ว

## การเปิดใช้
ต้องมี repository ปลายทางและ Discord Webhook ใน Secrets ก่อนเปิดใช้งานจริง ไม่ขอให้ผู้ใช้ส่ง webhook ในแชต เอกสารนี้เป็นแบบระบบ ยังไม่ใช่ระบบที่กำลังเฝ้าตรวจ
